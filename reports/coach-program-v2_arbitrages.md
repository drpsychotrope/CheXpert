# Arbitrages — `coach-program-v2` (C7)

Surfaced by the pre-V0 scan + 4 `/draft-general` cycles. **Defaults are the recommended
resolutions; the spec body already reflects them.** Ratify or override.

| # | Question | Options | **Default (applied)** | Why |
|---|---|---|---|---|
| **Q-A** | Budget toggle values **and scope** | (a) 15/30/60 like Insights, preview-only · (b) 15/30/60, also drives the launched Session · (c) other values | **(b) 15/30/60, drives BOTH preview and launched session** | Mirror Insights exactly (`insights.min15/30/60`) so the two surfaces agree — one mental model. The budget must reach `buildSession`, else the toggle is cosmetic: the program preview would shrink but the session the user actually runs stays at the hardcoded 30 (`Session.svelte:32`). Passing the chosen budget through `app.activeSession` closes that gap. Default 30 preserved (no behaviour change until the user picks). |
| **Q-B** | Mastery criterion: replace minutes, or add alongside? | (a) replace `minutes` with a criterion · (b) per-step criterion **with a minutes cap as a safety bound** · (c) minutes only (drop CO16) | **(b) criterion + minutes cap** | Drill-to-criterion ("until N-in-a-row" / recent miss-rate < X) is the product goal, but an open-ended drill with no bound can trap a struggling user forever and breaks the budget contract the toggle just established. A criterion **with** a minutes cap is honest and bounded: advance on mastery OR on the cap, whichever first. `minutes` stays (cap + back-compat with `buildSession`/`buildStudyPlan` which read it); the criterion is a NEW optional field → no PlanItem-consumer breaks. |
| **Q-C** | Closed loop: how efficacy feeds back | (a) descriptive surface only ("looks improved, moving on"), honesty-framed · (b) auto-advance/auto-resolve a weakness when recent miss-rate drops · (c) mutate the stored profile (mark weakness resolved on disk) | **(a) descriptive surface + a SOFT advisory; NO causal claim, NO auto-mutation** | Doctrine is honesty (`insights.didItMove`: "Descriptive, not proof … does not prove the training caused the change"). C7 reads the EXISTING `motifEfficacy` over stored analyses and shows, per weak motif in the program, the before/after miss-rate + a soft "looks improved — you can move on" *when `enoughData && deltaPct<0`*. It does **not** silently auto-drop a step (the user decides) and does **not** write "resolved" to the profile (that would be a causal claim on disk + a DB concern). Belt: a manual "mark as worked / advance" is the user's lever, mirroring Insights' descriptive posture. |
| **Q-D** | Opening-specific routing (CO17): generic → concrete line | (a) keep generic `repertoire`/`play-steered` (status quo) · (b) reuse `app.steerDimension` + name the most-played/weak opening from `eco.json` (descriptive), route to that · (c) auto-seed a concrete `RepertoireLine` from `OPENING_BOOK` | **(b) name a concrete opening from the player's analysed games via `eco.json`; keep routing book-agnostic; reuse the existing `play-steered` steer** | P4 (opening-steering-symmetry, V1) owns `OPENING_BOOK` and explicitly hands C7 the consume-only path: "C7 consumes `app.steerDimension` … completing the book makes that path work for either colour for free" (P4 §2) and "Coach C7 may later prefer a specific repertoire line … that routing lives in C7, consuming this completed book — not here" (P4 §11). So C7: (1) keeps the existing `play-steered` step (already biases via `selectOpening`), (2) UPGRADES the generic `repertoire` step's `reason` to NAME the player's most-played / weakest-scored opening (derived from analysed games with `nameOpening`/`localizedOpeningName`) when one is identifiable, falling back to the generic text otherwise. It does **NOT** add coach entries to `OPENING_BOOK` (AP-STEER-5) and does **NOT** auto-create a RepertoireLine (that is a user act). `focus` stays a stable routing key; only the bilingual `reason` gains the opening name. |

## Cross-cutting defaults also applied
- **No `DB_VERSION` bump.** All four folds are computational or additive-optional. (`DB_VERSION` stays 4.)
- **No new ADR by default.** Reuse ADR-0045 (coach) + 0039 (efficacy/session) + 0027 (study-plan budget) + 0014/0022 (loop). **Flag ADR-0059 ONLY** if the mastery-criterion step model (Q-B) is judged an architectural change to "what a program step is" (reserved 0054–0058 are taken). Do not pre-spend.
- **`buildCoachProgram` stays pure** (no `Date`/`Math.random`); the criterion is data, the efficacy read is injected by the UI.
- **Do NOT fork `buildStudyPlan`** (AP-COACH-1); Insights stays byte-identical. The new optional PlanItem field is omitted by `buildStudyPlan`, so its snapshot is unchanged.
- **Route only to non-empty modes** (AP-COACH-5): the named-opening upgrade is display-only on an already-routed `repertoire` step; the efficacy advisory never invents a step.

## Diminishing-returns note (4 cycles)
- **C1** found the 4 arbitrages above + the load-bearing constraint that `focus` is a routing key consumed by `buildSession`/`scenarioForFocus`/`app.steerDimension` (so opening routing must not translate `focus`).
- **C2** found the Session.svelte:32 second hardcoded `30` (→ Q-A scope (b)) and the mastery-cap honesty bound (→ Q-B (b)).
- **C3** found the efficacy key-mapping subtlety (MotifScore.theme → leakKey; 'endgame' is phase-scoped) and the no-auto-mutation honesty line (→ Q-C (a)).
- **C4** delta < 10%: only confirmed the P4 handoff direction is one-way (consume, never edit) and that no new persisted field is needed. **Stopped at 4** (cycle-4 surfaced no new arbitrage, only hardening of existing ones).
